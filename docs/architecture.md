# 아키텍처

## 전체 구조

```
[React 채팅 UI] ──HTTP──▶ [FastAPI]  src/backend/main.py
                               │
                               ▼
        ┌──────────────── Supervisor (LangGraph) ─────────────────┐
        │ 1. 요청 해석: 입력 추출(LLM) + 이전 상태와 비교 → 의도 판정 │
        │ 2. 입력 확인: 월령·출발지·날짜 (빠지면 되묻기)              │
        │ 3. 다시 실행할 범위 결정 → 서브그래프에 일임                │
        │ 4. 결과 취합 → 순위 (가족 나들이 기준, 아래 참고) → 응답    │
        └─────────────────────────────────────────────────────────┘
          │ ①                  │ ② 후보별 병렬 (Send)          │ ③ 후보 전체 (취향이 있을 때)
          ▼                    ▼                               ▼
  [장소 탐색]          [환경]       [후기·적합도]          [취향 매칭 · RAG]
  출발지 좌표 확인      날씨 조회     네이버 후기 수집        기준 장소 조회 (유사 장소 요청)
  월령별 반경 계산      미세먼지 조회 월령 적합도 판정·요약   장소 프로필 생성 · 임베딩
  TourAPI + 카카오 수집 나쁜 날 판정  실내/야외 판정          취향 질의와 유사도 · 근거 문장
  (취향 키워드 추가 검색)                                     retriever.py
  같은 장소 병합 · 편의시설
          │                    │                               │
          └────────────▶ [도메인 도구 · tools.py] ◀────────────┘
                         외부 API · 임베딩 호출 · 타임아웃(5초/20초) · 부분 실패 처리
```

- **Supervisor만 대화를 안다.** 서브그래프는 입력을 받아 정해진 구조의 데이터를 돌려주는 순수 처리 단위다.
- **LLM은 흐름을 결정하지 않는다.** Supervisor는 입력 추출에만 LLM을 쓰고(고정 JSON), 분기는 규칙으로 정한다. 서브그래프 안의 LLM·임베딩 호출도 정해진 단계 안의 도구 호출이다.
- **외부 글(블로그·카페)은 후기·적합도와 취향 매칭 서브그래프 안에서만 다룬다.** 장소 프로필에 들어간 후기 문장은 임베딩·근거 표시용 데이터로만 쓰고, 그 안의 지시문은 따르지 않는다.

## 서브그래프 흐름

각 서브그래프는 `build_graph(prov)`로 Providers를 묶어 컴파일하고, `run(graph, ...)`으로 실행한다. Providers는 그래프 상태에 넣지 않는다.

```
장소 탐색   START → radius → collect ─┬→ facilities (후보별 Send, 병렬) → attach → END
                                       └→ attach (후보 없음)
환경        START ─┬→ weather ─┬→ judge → END
                    └→ dust ────┘
후기·적합도 START → fetch_reviews → judge ─┬→ classify_llm → END   (카테고리로 실내/야외 판단 불가)
                                            └→ END                   (카테고리 규칙으로 결정)
취향 매칭   START → build_query ─┬→ build_profiles → index ─┬→ score → END
                                  ├→ skip → END (질의 없음)   └→ END (임베딩 실패)
                                  └→ unavailable → END (임베딩 미설정)
```

- **후보 수집 (`collect`):** TourAPI(관광지·문화시설·레포츠)와 카카오(관광명소·문화시설 + 공원·키즈카페·동물원 키워드)를 반경 안에서 모은다. 둘 다 반경이 최대 20km라, 더 넓으면 TourAPI는 중심 + 바깥 고리 6곳에서 나눠 검색한다. 아기 나들이에 맞는 종류만 허용 목록으로 남긴다 (TourAPI `cat3` 코드, 카카오 카테고리명).
- **날씨 (`integrations/kma.py`):** 오늘~4일 뒤는 단기예보(5km 격자)의 09~18시 값, 그 이후 10일 뒤까지는 중기예보(가장 가까운 예보 도시의 기온 + 육상예보 구역의 오전·오후 강수확률)를 쓴다. 단기예보 마지막 날에 낮 시간 값이 없으면 중기예보로 넘어간다. 응답은 30분 동안 캐시해 날짜만 바뀐 재조회의 호출을 줄인다.
- **미세먼지 (`integrations/airkorea.py`):** 오늘~모레는 일별 예보의 PM10·PM2.5 등급(좋음~매우나쁨), 그 뒤 약 5일 뒤까지는 주간예보의 PM2.5(낮음/높음, 높음은 나쁜 날)를 쓰고, 그보다 뒤는 "미세먼지 예보 없음"이다. 예보 권역은 카카오 좌표→행정구역으로 정한다(경기 남·북부, 강원 영서·영동, 광주·전남 구분). 조회 실패 시 가장 가까운 권역 중심을 쓴다.
- **같은 시설 묶기 (`group_facilities`):** 띄어쓰기를 뺀 이름의 공통 앞부분(4글자 이상)이 한쪽 이름의 첫 단어 전체이고 1km 안에 있으면 한 시설로 묶는다(예: 서울대공원 / 서울대공원 제1아프리카관). 카드 이름은 공통 이름("서울대공원")으로 보여주고, 묶인 항목 이름은 카드의 `includes`에 남긴다. 위치·편의시설에 쓰는 대표 항목은 공통 이름만 있는 항목이 있으면 그것, 없으면 공통 이름을 뺀 부분의 나들이 등급이 가장 높은 항목("산림욕장"보다 "어린이동물원") → 짧은 이름 → TourAPI 등록 순이다.
- **후보 선정 (`preselect`, 15곳):** 거리 구간(0~5km / 5~20km / 20km~반경)마다 같은 몫을 뽑는다. 구간 안에서는 나들이 목적지 등급(`outing_grade` — A: 동물원·테마파크·아쿠아리움·수목원·생태/습지공원·과학관·체험농장·대공원·"어린이" 장소, B: 박물관·체험·호수·민속마을·고궁·공원, C: 키즈카페·실내 놀이터·도서관·갤러리·근린공원) → 대표 사진 있음 → 가까운 순. 몫을 못 채운 구간의 자리는 나머지 중 상위로 채운다.
- 실패한 외부 API는 각 서브그래프의 `failed_sources`(누적 리듀서)에 모인다.
- 편의시설 최종 판정(공공데이터 → 후기 언급 → 정보 없음)은 장소 탐색과 후기 결과가 모두 필요해서 Supervisor가 합칠 때 `place.resolve_facilities`로 한다.

## 취향 매칭 (RAG)

| 단계 | 내용 |
|---|---|
| (Supervisor) `check_reference` | 기준 장소를 이름으로 전국 키워드 검색하고(`preference.resolve_reference`) 설명·후기 문장으로 프로필을 만든다. 반경 밖이어도 된다. 못 찾으면 다시 묻고("없음"이면 기준 장소 없이 진행), 여러 곳이면 번호로 고르게 한다. 조회 자체가 실패하면 기준 장소 없이 진행하고 안내한다 |
| `build_query` | 질의 = 취향 문장 + 기준 장소 프로필 문장(최대 6개). "OO은(는) 관광지입니다" 같은 틀 문장은 모든 후보와 비슷하게 나와서 기준 장소 질의에서 뺀다 |
| `build_profiles` | 후보별 문서 = 장소명 · 카테고리 · TourAPI 개요 · 실내/야외 · 편의시설 · 후기 요약문. 문장 단위로 나눠 근거 추적에 쓴다 |
| `index` | Bedrock 임베딩(Titan)으로 문장을 임베딩해 메모리 내 벡터 저장소에 넣는다 (`retriever.py`, 요청마다 생성, DB 저장 없음) |
| `score` | 후보별로 질의와 가장 가까운 문장의 코사인 유사도로 일치 수준을 정한다(0.55 이상 높음, 0.40 이상 보통, 그 밖은 낮음). 0.40 이상인 문장만 근거로 최대 2개 붙인다 (`doc_id` = `<장소키>#<문장번호>`). 기준값은 실제 임베딩 모델로 평가하며 조정한다 |

- **추가 검색 규칙:** 기존 후보로 먼저 매칭한다. 상위 5곳 중 일치 수준 "높음"이 3곳 미만이면, 파이프라인의 `augment`가 취향 키워드(LLM 추출, 없으면 규칙)로 반경 안을 키워드 검색해 새 후보만 추가로 평가한다. 같은 키워드로는 한 번만 검색한다.
- **재사용:** 매칭 결과는 세션에 저장한다. 날짜만 바뀌면 같은 질의·같은 후보이므로 임베딩을 다시 호출하지 않는다.
- **순위 반영:** 일치 수준은 안전 기준(나쁜 날의 야외 장소) 다음, 나들이 목적지 등급 앞에 반영한다. 유사도 점수의 작은 차이가 순위를 흔들지 않도록 점수 대신 수준(3단계)을 쓴다.
- **RAGAS 평가:** 취향 질의를 question, 카드에 붙은 근거 문장을 contexts로 쓴다.

## Supervisor 그래프

```
START → extract → classify ─┬→ reset → check_age …
                             ├→ detail → END                (저장된 카드로 응답)
                             ├→ out_of_scope → END
                             └→ check_age → check_nap → check_departure → check_date
                                   → check_reference → plan → delegate → END
(check_* 중 하나가 되묻기를 만들면 그 턴은 END)
```

- `plan`: 직전 검색에 쓴 입력(`searched`)과 지금 입력을 비교해 의도와 재실행 범위(`full` / `environment` / `rerank`)를 정한다.
- `delegate`: 일임 파이프라인([supervisor/pipeline.py](../src/backend/supervisor/pipeline.py))을 실행한다. Providers는 상태가 아니라 실행 설정(`config["configurable"]["providers"]`)으로 받는다.

일임 파이프라인:

```
START ─┬─ full ────────▶ search ─┬─▶ evaluate (새 후보별 Send: 환경 ‖ 후기) ─▶ match
       ├─ environment ─▶ refresh_env (저장된 후보별 Send) ──────────────────▶ match
       └─ rerank ──────────────────────────────────────────────────────────▶ match
match (취향 매칭 서브그래프) ─▶ rank (안전 → 취향 → 나들이 등급 → 적합도 → 편의시설 → 거리, 같은 종류 최대 2곳)
rank ─┬─▶ widen ─▶ search                (full 범위, 5곳 미만, 아직 넓히지 않음)
      ├─▶ augment ─▶ evaluate / match    ("높음" 3곳 미만, 새 키워드)
      └─▶ finish ─▶ END
```

## Supervisor 의도 판정과 재실행 범위

이번 메시지에서 추출한 입력(LLM, 고정 JSON)을 직전 상태와 비교하고, 장소를 가리키는 표현이 있는지 확인해 규칙으로 판정한다.

| 의도 | 예시 | 장소 탐색 | 환경 | 후기·적합도 | 취향 매칭 | 순위 |
|---|---|:-:|:-:|:-:|:-:|:-:|
| 새 추천 (입력 완성) | "18개월, 강남역, 토요일" | O | O | O | 취향이 있으면 O | O |
| 날짜 변경 | "일요일로 바꿔줘" | – | O | – | – | O |
| 출발지 변경 | "판교에서 출발할게" | O | O | O | 취향이 있으면 O | O |
| 월령·낮잠 변경 | "아 24개월이에요" | O (반경 변경) | O | O (적합도 변경) | 취향이 있으면 O | O |
| 취향 추가·변경 | "실내 위주로, 조용한 곳" | 근거 부족 시 키워드 추가 검색 | 추가 후보만 | 추가 후보만 | O | O |
| 유사 장소 | "서울숲 좋았는데 비슷한 곳" | 근거 부족 시 키워드 추가 검색 | 추가 후보만 | 추가 후보만 | O (기준 장소 조회 포함) | O |
| 장소 상세 | "2번째 곳 더 알려줘" | – | – | – | – | – (저장된 카드로 응답) |
| 새로 시작 | "처음부터 다시" | 상태 초기화(취향 포함) 후 되묻기 | | | | |
| 범위 밖 | "아기 이유식 추천해줘" | 서비스 범위 안내 | | | | |

- 필수 입력(월령·출발지·날짜)이 모이기 전에 취향이나 기준 장소를 말하면 저장해 두고 되묻기를 계속한다.
- 이전 실행 결과(후보, 장소별 환경·후기 결과, 취향 매칭 결과, 카드)는 세션 상태에 저장하고, 재실행하지 않는 단계는 저장된 결과를 재사용한다.
- 변경된 입력이 잘못되면(지난 날짜, 월령 범위 밖, 기준 장소를 못 찾음 등) 서브그래프를 실행하지 않고 되묻는다. 이전 추천 결과는 유지한다.

## 파일 배치

```
src/backend/
├── main.py              # FastAPI 진입점
├── api/                 # 우리가 제공하는 API
│   ├── chat.py          # POST /chat: 세션 · 한 턴 실행 · 결과 카드 · 오류 처리
│   └── schemas.py       # 요청 / 응답 형식
├── agent.py             # Supervisor 그래프 (메시지 분류 · 되묻기 · 재실행 범위 · 일임)
├── tools.py             # 도메인 도구 계약 (Providers) · 타임아웃 · 실패 기록
├── retriever.py         # RAG: 장소 프로필 문장 · 메모리 벡터 저장소 · 코사인 검색
├── supervisor/          # agent.py가 쓰는 부품
│   ├── intent.py        # 입력 추출(규칙) · 의도 판정 · 재실행 범위 결정 (순수 함수)
│   ├── pipeline.py      # 일임 파이프라인 (장소 탐색 → 후보별 환경·후기 → 취향 매칭 → 순위 · 다양성)
│   └── cards.py         # 결과 카드 생성 (고정 필드)
├── agents/              # 서브에이전트
│   ├── place.py         # 장소 탐색 서브그래프 (반경 · 후보 수집 · 편의시설 조회)
│   ├── candidates.py    # 후보 처리 규칙 (정규화 · 병합 · 같은 시설 묶기 · 나들이 등급 · 후보 선정)
│   ├── environment.py   # 환경 서브그래프 (날씨 · 미세먼지 · 나쁜 날 판정)
│   ├── review.py        # 후기·적합도 서브그래프 (후기 · LLM 판정·요약 · 실내/야외)
│   └── preference.py    # 취향 매칭 서브그래프 (기준 장소 조회 · 프로필 · 임베딩 유사도)
├── prompts/             # LLM에게 무엇을 물을지 (프롬프트 · 답 스키마 · 답 검증)
│   ├── judge.py         # 월령 적합도 기준 · 후기 요약 규칙 · 판정 답 검증
│   ├── extract.py       # 입력 추출
│   ├── setting.py       # 실내/야외 분류
│   └── common.py        # 장소 정보 블록
├── integrations/        # 연동 서비스 (어떻게 부를지)
│   ├── kakao.py         # 카카오 로컬: 출발지 좌표 · 반경 내 장소 · 키워드 · 좌표→행정구역
│   ├── tourapi.py       # TourAPI: 반경 내 장소 · 편의시설(소개·무장애) · 개요 · 키워드
│   ├── naver.py         # 네이버 검색 (NAVER API HUB): 블로그·카페 후기 요약문
```

`Providers`의 선택 호출: `keyword_search`(키워드 장소 검색, TourAPI·카카오), `embed`(텍스트 임베딩, Bedrock). 없으면 취향 매칭 없이 추천하고 안내한다. 입력 추출 LLM은 `Deps.extractor`로 주입한다.

## Bedrock

| 용도 | (지역, 모델) 체인 — 429면 다음 항목 | 호출 |
|---|---|---|
| 월령 적합도 판정 · 후기 3줄 요약 (Sonnet만) | us-west-2 `us.`4.6 → ap-northeast-2 `global.`4.6 → us-east-1 `us.`4.6 → us-west-2 `global.`4.6 → Sonnet 4.5 조합들 | Anthropic SDK `AnthropicBedrock` (지역별 클라이언트). 도구 호출을 강제(`tool_choice`)해 정해진 스키마의 JSON으로만 받고, 받은 뒤 다시 검증한다 |
| 입력 추출(매 메시지, Haiku 4.5) | ap-northeast-2 `global.` → us-east-1 `global.` → us-west-2 `global.` | 같은 방식 |
| 실내/야외 판정 (Haiku 4.5) | us-west-2 `us.` → us-east-1 `us.` → us-west-2 `global.` | 같은 방식 |
| 임베딩 (취향 매칭) | `amazon.titan-embed-text-v2:0` (512차원, 정규화) | `boto3` `bedrock-runtime` `invoke_model`. 한 번에 한 문장이라 병렬 호출 + 프로세스 내 캐시 |

- `anthropic` SDK는 1.17.0으로 고정한다. 2.x는 API 버전 `2026-10-21`을 보내는데, Bedrock은 이 버전을 Claude 4.7 이상에만 받는다.
- 요청 한도: Bedrock 한도는 지역·모델·추론 프로파일(`global.`/`us.`)별로 잡히고 계정을 여러 사람이 함께 쓰므로, 작업마다 다른 지역·모델에서 시작한다(us-east-1, us-west-2, ap-northeast-2). 429(일일 토큰 한도 등)가 나면 체인의 다음 모델로 넘어간다. 모델별 동시 요청은 제한한다(판정 6, 추출·분류 8, 나머지는 대기). SDK 재시도는 1번이고, Titan은 boto3 `adaptive` 모드로 재시도한다. 대기와 재시도를 포함한 제한 시간은 20초다.
- 작업별 체인은 `.env`의 `BEDROCK_JUDGE_MODELS`, `BEDROCK_EXTRACT_MODELS`, `BEDROCK_CLASSIFY_MODELS`에 `지역/모델ID`를 쉼표로 이어 바꿀 수 있다(지역을 빼면 `BEDROCK_REGION`). 지역은 `BEDROCK_REGION`, 임베딩은 `BEDROCK_EMBED_MODEL_ID` (없으면 기본값).

## 공통 원칙
- 외부 API 하나가 실패하거나 제한 시간(공공·검색 API 5초, Bedrock LLM·임베딩 20초) 안에 응답하지 않으면 해당 항목만 "정보를 불러오지 못함"으로 표시한다. 임베딩이 실패하면 취향 매칭 없이 기존 순위로 추천하고 그 사실을 안내한다.
- API 키는 저장소 루트 `.env`에만 두고 백엔드에서만 사용한다.
- API 요청·응답 형식은 [api-spec.md](api-spec.md)를 참고한다.
